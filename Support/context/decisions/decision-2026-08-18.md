# Decision Log - 2026-08-18

## Decisions

### 1. The dated todo and worklog files are retired

- `worklog/todo-2026-08-16.md` and `worklog/worklog-2026-08-16.md` are deleted.
- This supersedes decision 3 ("Dated todo naming") and decision 6 ("Todo centralization") in
  [`decision-2026-08-16.md`](decision-2026-08-16.md).
- Reason: one dated checklist could not hold a product of this size. By the time eighteen plan
  files existed, the dated file was claiming ownership of tracking it no longer performed, and the
  dated worklog was repeating narrative the plans already recorded. Two files describing the same
  work is how a project starts lying to itself.
- Nothing was discarded. Every item was moved into the plan that owns the surface it describes;
  the mapping is recorded in `worklog/BRM-Plan-todo.md` under **Retired files**.

### 2. `worklog/BRM-Plan-todo.md` is the master index

- It is the single entry point to delivery tracking, and the only file allowed to see everything.
- It holds no tasks. It links every plan, mirrors each plan's own count, states where a new task
  goes, and maps each requirements section to its owning plan.
- A plan that is not linked from the index does not exist as far as the project is concerned.

### 3. One plan per area, named `Plan-<Area>-todo.md`

- `worklog/` contains only the master index, `Plan-*` files, this folder's README, and `assets/`.
- Each plan owns exactly one surface — a window region, a tab, a feature, or an engineering area —
  and opens with a boundary statement saying what it does not own.
- Work that spans two plans belongs to the one that owns the **visible surface**; the other links
  to it rather than restating it.

### 4. Narrative lives in the plan that owns the work

- There is no separate story file. What shipped is recorded in the owning plan, usually as an
  "Already shipped" list or a verification section.
- Cross-cutting evidence — build and test runs, measurements, what has actually been click-tested
  in the GUI — is collected in `worklog/Plan-QualityVerification-todo.md`.
- Release artifacts, staging, tagging and publication are owned by
  `worklog/Plan-ReleasePackaging-todo.md`.

### 5. READMEs route to the master index, not to a dated file

- The root `README.md`, the Support handbook, the Context README, and the
  build-release documents all link to `worklog/BRM-Plan-todo.md` when they need to point at
  current work.
- No document outside `worklog/` names an individual plan as *the* tracker; they name the index,
  and the index routes onward.

### 6. The workspace is flat: no `LXC-BRM/` container

- Everything that lived in `LXC-BRM/` moves to the repository root: `App/`, `Tests/`, `Support/`,
  the Xcode project, and the contributor documents.
- Reason: 124 of 127 tracked files were already inside that folder, so the container was the
  repository spelled twice — and the duplication had gone wrong in practice. Two `LICENSE` files
  disagreed (Apache 2.0 at the root, MIT inside), there were two `.gitignore` files, two READMEs
  with overlapping content, and a CI workflow that assumed a root layout the repository did not
  have and therefore failed on every push.
- Paths inside `project.pbxproj` are project-relative, so moving the whole tree together left them
  valid. Verified by a clean build and a full test run after the move.
- This supersedes decision 1 ("organized as an Xcode project under `LXC-BRM/`"), the folder half
  of decision 2, and decision 9's phrase "inside `LXC-BRM/`" in
  [`decision-2026-08-16.md`](decision-2026-08-16.md).

### 7. `LXC-BRM` was a codename and is retired

The product is **LXC Build Release Manager**. The abbreviation survives only where a hyphenated
identifier is required.

| Was | Now |
| --- | --- |
| `LXC-BRM.xcodeproj` / `.xcworkspace` | `LXC-Build-Release-Manager.xcodeproj` / `.xcworkspace` |
| Targets `LXC-BRM`, `LXC-BRMTests` | `LXC-Build-Release-Manager`, `LXC-Build-Release-ManagerTests` |
| Swift module `LXC_BRM` | `LXC_Build_Release_Manager` |
| `App/LXC_BRMApp.swift`, `struct LXC_BRMApp` | `App/BuildReleaseManagerApp.swift`, `struct BuildReleaseManagerApp` |
| `com.lexvoraconsulting.brm` | `com.lexvoraconsulting.buildreleasemanager` |
| `~/Library/Application Support/LXC-BRM/` | `~/Library/Application Support/LXC-Build-Release-Manager/` |
| `~/Library/Logs/LXC-BRM/` | `~/Library/Logs/LXC-Build-Release-Manager/` |
| `.derivedData-lxc-brm/` | `.derivedData/` |
| `lxc-brm-mark.svg` | `brand-mark.svg` |

- The Application Support rename is migrated, not abandoned: `AppDataLocations` moves the old
  folder to the new name once, and only when the new folder does not exist yet, so a migrated
  install can never be overwritten by a stale legacy folder.
- The bundle identifier change means macOS treats this as a new application: notification
  permission and the launch-at-login registration are re-established on first run.

### 8. One license, MIT, at the root

- The repository is public and MIT-licensed: `Copyright (c) 2026 Lexvora Consulting`.
- The Apache 2.0 file that sat at the root was removed. It contradicted the MIT file inside
  `LXC-BRM/` and every README badge, and because GitHub reads the root file, the repository was
  publicly advertising the wrong license.
- There is exactly one `LICENSE`, at the root, and the READMEs point at it.

### 9. Support is a filesystem-synchronized group in Xcode

- `Support/` is registered as a `PBXFileSystemSynchronizedRootGroup`, so the Xcode navigator shows
  the whole documentation tree and stays correct as plans are added and removed. The previous
  hand-maintained group listed 34 of the files and had already gone stale.
- It is deliberately **not** a member of any target: documentation must never become an app
  resource again. Verified — the built bundle contains only `hi.lproj` and the background asset.
- The project also gained its first **shared** scheme. There was none, so `-scheme` worked only on
  a machine where Xcode had auto-generated a private one, which is why CI could never be trusted.

## Window Layout & View Menu (v0.1.2)

Tracked in `Plan-WindowLayout-todo.md`. This pass touched the app shell only — no tab content.

**What was wrong.** The left repository container could not be resized with the mouse: the
sidebar used the single-value `.navigationSplitViewColumnWidth(_:)`, which pins the column and
makes macOS drop the drag handle. The sidebar footer ("Open Repository…" and the gear
"Preferences" button) was being clipped by the bottom status bar, because the status bar was a
`safeAreaInset` on the whole `NavigationSplitView` and that inset does not propagate into the
sidebar column's own safe area. There was also no `.commands` block anywhere in the app, so the
View menu had no entries at all, and the right-hand detail panel's visibility lived in a
`@State` private to `RepositoryDetailView`, unreachable from a menu command.

**What shipped.**

- Three layout flags added to `Preferences` (`showStatusBar`, `showRepositorySidebar`,
  `showDetailInspector`), persisted to `preferences.json` like every other setting.
- `PreferencesStore.binding(_:)` added so menu commands and views can toggle one flag without
  rebuilding the whole `Preferences` value at each call site.
- Sidebar column switched to `min: 180, ideal: <saved width>, max: 420` — the drag handle is
  back and the Appearance preference still seeds the starting width.
- Status bar moved out of `safeAreaInset` into a plain `VStack` sibling below the split view,
  so the sidebar footer can never be clipped by it again.
- New `LayoutCommands` block in `LXC_BRMApp.swift` adds the three items to the View menu via
  `CommandGroup(after: .sidebar)`, each rendered as a checked `Toggle`.
- `showInspector` lifted out of private `@State` and bound to the shared preference, so the
  existing "Toggle Build Panel" toolbar button and the new menu item stay in agreement.
- Version bumped to `0.1.2` (`CURRENT_PROJECT_VERSION` 2) in both build configurations.

**How it was verified.** `BUILD SUCCEEDED` with no new warnings. The three menu items were
confirmed present in the *live* View menu through an accessibility query, then clicked through
the real menu while watching `preferences.json` change on disk. Screenshots captured with all
panels visible and all three hidden. The sidebar toggle was round-tripped off→on→off after the
visibility binding was reworked to a single derived source (the first two-way `onChange`
version could latch and stop responding).

**Caveat.** Sidebar visibility does not survive a relaunch. The status bar and detail panel do.
macOS window-state restoration re-expands the split view's sidebar on launch and writes that
back through the visibility binding, overwriting the saved `false`. A delayed guard on the
binding setter was tried, did not hold, and was removed rather than left in as a hack. Hiding
and showing the sidebar works correctly for the whole session; it just reopens visible.

This is the first part of the app that has actually been click-tested in the running GUI rather
than only compiled and traced — the standing "no GUI click-through testing yet" caveat in
`todo-2026-08-16.md` no longer applies to these three controls.

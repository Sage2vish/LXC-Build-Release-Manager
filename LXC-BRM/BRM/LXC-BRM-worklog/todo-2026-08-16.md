# todo-2026-08-16

All active todo tracking lives here, and only here. Source: `LXC-BRM-context/requirements.md` (in-repo copy of `LXC-BuildManager.pdf`), read against `LXC-BRM-context/decisions/decision-2026-08-16.md`.

No other BRM folder keeps a todo file. Work is broken into phases so it ships in reviewable slices instead of one big drop. Phases are built in order; a phase doesn't start until the one before it is at least functional.

## Phases

### Phase 0 — Workspace Foundation
1. Native Swift/SwiftUI app scaffold under `LXC-BRM/`, Xcode-openable.
2. BRM folder layout: shared, frameworks, build-release, worklog, context.
3. Rules, architecture, decisions, and requirements captured in `LXC-BRM-context/`.
4. Single todo file convention, enforced in this file and the worklog README.
5. App follows the system light/dark appearance (no forced color scheme).

### Phase 1 — Repository Input & Detection (requirements.md §1)
1. Accept a GitHub repo URL or a local folder path as input; validate the format.
2. Add a repo via a local folder picker (NSOpenPanel) or a pasted GitHub URL.
3. Scan the repo root for `/build`; show "No `/build` folder found" when missing.
4. Scan `/build/scripts/` for `.sh` files when `/build` exists; show "No build scripts found in `/build/scripts/`" when empty.
5. Convert each script filename into a readable label (`build-ios.sh` → "build-ios").
6. Persist a "Recent Repositories" list across launches (local JSON); support re-open and remove without deleting the folder.
7. Support opening and switching between multiple repos in one session; each keeps its own discovered scripts.

### Phase 2 — Build Execution & Management (requirements.md §2)
1. Display each discovered script as a clickable command button.
2. On click, run `bash /path/to/repo/build/scripts/script-name.sh` as a background subprocess, working directory = repo root.
3. Stream stdout/stderr live, line by line, each line timestamped.
4. Track status per build: In Progress (spinner), Success (✓ + duration), Failed (✗ + duration).
5. Add a Cancel/Stop control; cancelling preserves partial output and sets status to "Cancelled".

### Phase 3 — Log Storage & Retrieval (requirements.md §3)
1. Write a log file to `/build/logs/` per run: `build-YYYY-MM-DD-HH-MM-SS.log`, full stdout+stderr, plain text.
2. View current (live) and past build logs from history.
3. Monospace, terminal-style log view with per-line timestamps, scrollable.
4. In-log search: highlight matches, show match count, next/previous navigation.
5. Log filters: Errors Only, Warnings Only, Info Only.
6. Export current log to Downloads (or chosen location) as `.log` or `.txt`.

### Phase 4 — Project & Build Overview (requirements.md §4)
1. Show repo name, path/URL, connection status, and total builds run this session.
2. List build commands with label, last-run time, and success/failure/never badge.
3. Per-repo build history: script, timestamp, status, duration for every run.
4. Compute success rate and average build duration per repo.
5. Quick-stats cards: total builds this session, success rate, most recently run, last failed build.

### Phase 5 — Multi-Repository Support (requirements.md §5)
1. List all opened/recent repos; switching is instant, no loading screen.
2. On switch: refresh build buttons, clear log display, reload stats and history.
3. Keep build history isolated per repo.
4. Add/remove/pin (favorite) repos; removing only clears the app entry.

### Phase 6 — Non-Functional Hardening & v1 Scope Check
1. Launch under 2 seconds; repo scan under 5 seconds.
2. Graceful error handling for network issues and missing/unreachable repos.
3. Verify 5-10+ connected repos without visible slowdown.
4. Keep the codebase simple, minimal dependencies, easy to extend.
5. Verify offline use: logs/history viewable, GitHub fetch fails gracefully.
6. Confirm every v1 scope item from `requirements.md` is met, and nothing out-of-scope (GitHub Actions, webhooks, Slack/email, Docker, Windows/Linux, analytics/charts) crept in.

### Phase 7 — Packaging & Deliverables
1. Build instructions for packaging the `.app`.
2. User guide / quick start.
3. Configuration template (`projects.json`) kept current in `LXC-BRM-build-release/`.
4. Tag a release and stage the `.dmg` in `LXC-BRM-build-release/version/`.

## Decision Overrides In Effect

1. Stack: native Swift/SwiftUI, not Tauri/Rust/React — every phase above is built natively.
2. Storage: `projects.json` under `LXC-BRM-build-release/` for repo/script config, not a generic local JSON path.
3. Any new PDF-vs-decision conflict gets recorded in `LXC-BRM-context/decisions/` before being built around.
